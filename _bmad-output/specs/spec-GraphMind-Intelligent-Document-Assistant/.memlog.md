- (decision) Why: trust-first core insight -- user should never need to open source documents to trust an answer; citations + honest refusal are the mechanism. Portfolio project, 2 devs, 20-day fixed window, intent to keep evolving post-course.
- (capability) CAP-1 Authentication and Tenancy Isolation (FR-1, FR-2). intent: a visitor can create an account, log in, and every subsequent read/write to vector index and knowledge graph is filtered by user_id server-side, never trusting client input. success: passwords hashed (bcrypt_sha256), JWT session; two test accounts cannot retrieve each others documents/citations/graph data through any endpoint. Launch blocker per PRD, not best-effort.
- (capability) CAP-2 Document Ingestion (FR-3, FR-4, FR-5, FR-6, FR-14). intent: user uploads PDF/MD/HTML; system parses into passages tagged with metadata, embeds them, and in parallel extracts entities/relationships merged into the users single unified knowledge graph; user sees per-document ingestion status; unchanged content is not reprocessed; drag-and-drop upload with independent per-file progress. success: unsupported formats rejected before processing; each document shows one of Uploaded/Extracting/Graphing/Ready/Failed with Failed carrying a human-readable reason; re-uploading a byte-identical file skips extraction/embedding calls; matching entities merge rather than duplicate.
- (capability) CAP-3 Document Library (FR-7, FR-8). intent: user can list, inspect, and delete their own documents only. success: document list shows only the authenticated users documents; opening one shows status/upload date/chapter breakdown; deleting removes the document and its passages/embeddings from the vector index immediately, while knowledge-graph entities derived from it are not retroactively pruned, and the UI states that boundary plainly at delete time.
- (capability) CAP-4 Grounded Chat Q&A (FR-9, FR-10, FR-11). intent: user asks a question; system retrieves relevant passages and/or traverses the knowledge graph and returns a cited answer, or explicitly refuses when evidence is inadequate; user can scope a question to all or a chosen subset of documents. success: every claim-bearing sentence in an answer traces to at least one passage-level citation; below a defined relevance threshold the system short-circuits before generation and returns an explicit refusal; passages outside the selected document scope never appear as citations; default scope is all documents.
- (capability) CAP-5 Knowledge Graph View (FR-12). intent: user can visually explore their own unified knowledge graph as an interactive node-link diagram, scoped to their user_id. success: the view renders entities/relationships as a node-link diagram; no other users graph data is queryable or renderable from this view.
- (capability) CAP-6 Evaluation Harness (FR-13). intent: a single command runs a fixed evaluation set against the live system and reports accuracy on answerable questions and refusal-rate on unanswerable ones. success: harness invokes the service layer directly (not through the UI); output reports both metrics numerically; evaluation set contains 15-20 question/expected-answer pairs spanning single-source factual, cross-document synthesis, and unanswerable categories, authored incrementally during build.
- (capability) CAP-7 Account and Appearance Settings (FR-15, FR-16). intent: user can switch light/dark theme as a manual persisted preference, and can permanently delete their own account with an explicit confirmation step. success: theme choice persists across sessions and every screen (including auth pages) renders correctly in both themes; account deletion requires explicit confirmation and, on confirm, removes the users documents, vector entries, knowledge-graph data, and account record, then logs the user out.
- (constraint) Per-user tenancy isolation is a launch blocker (SM-3): any cross-tenant leak is not a bug to triage later -- it blocks release. Enforced server-side at the query layer on both Weaviate and Neo4j, never only in the UI.
- (constraint) Hybrid retrieval architecture (Weaviate vector index + Neo4j unified per-user knowledge graph) is non-negotiable -- vector search answers semantic questions, graph traversal answers relational questions; neither alone satisfies the products trust bet.
- (constraint) All managed services must run on free tiers (Weaviate Cloud free, Neo4j AuraDB free, OpenRouter free, Neon Postgres free, Vercel Hobby, Render free web service) so the project is reproducible by any reviewer at zero cost; ingestion content-hash dedupe exists specifically to protect this constraint.
- (constraint) Fixed 20-day delivery window with a 2-developer team drives KISS/YAGNI throughout: feature-based modular monolith over layered/hexagonal architecture, minimal auth schema (no password reset/email verification), no staging environment, exact-match-only entity resolution, React Context over Redux.
- (constraint) Refusal below evidence threshold (FR-10) is a required safety guardrail, not an optional nicety -- it must short-circuit before any generation call.
- (nongoal) No cross-tenant collaboration, sharing, or team workspaces in v1 -- each accounts documents are visible only to that account.
- (nongoal) No proactive/unprompted insights such as contradiction detection across a users documents in v1 (identified as strong v2 direction, not lost).
- (nongoal) No correction-feedback loop that improves extraction quality over time, and no user-editable correction of extracted entities/relationships, in v1.
- (nongoal) No reference-counted/provenance-aware graph deletion in v1 -- deleting a document clears its vector passages but does not retroactively prune graph entities derived from it; UI discloses this boundary at delete time.
- (nongoal) No answer confidence badge/score display -- explicitly rejected during brainstorming convergence, revisit only if user feedback demands it.
- (nongoal) No chapter-level filtering in Chat -- v1 document scoping is document-level only; chapters remain captured as metadata and visible in Document Detail but are not user-filterable in Chat.
- (nongoal) Query history (question + answer + scope + citation snapshot) is deferred to v2, decided during UX design -- no history surface in v1.
- (nongoal) Not a general-purpose chatbot: GraphMind never answers from the LLMs general knowledge when the corpus doesnt support an answer -- this is the core differentiator, not a limitation.
- (nongoal) No clickable citations that open/highlight source passage inline, no conversational memory/follow-ups, no suggested follow-ups, no document search/filtering, no project/category grouping beyond chapters, no hybrid BM25+vector search, no raw-context inspection panel, no conversation export, no account-deletion recovery/undo window, no live entity/relationship preview post-ingestion, no natural-language querying over the graph -- all v1 out-of-scope per PRD 6.2 backlog.
- (note) Success signal (SM-1..SM-3, SM-C1): SM-1 answerable-question accuracy on the Evaluation Set >=80% (assumption, adjust once baseline exists), validates FR-9/FR-10/FR-13. SM-2 refusal correctness = 100% of genuinely unanswerable eval questions refused, validates FR-10/FR-13. SM-3 zero cross-tenant data leakage verified with two test accounts, validates FR-2, tiered Primary since tenancy is a launch blocker. Counter-metric SM-C1: refusal rate on answerable questions must not rise as a side effect of chasing SM-2 -- over-refusing is as much a failure as fabricating. Course Definition of Done: all PRD 6.1 in-scope items function end-to-end and demonstrable; every chat answer shows at least one concrete source reference; unanswerable questions produce explicit refusal verified by the Evaluation Set; a user cannot retrieve another users documents (two test accounts); evaluation script runs single-command with numeric accuracy output.
